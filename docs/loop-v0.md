# 调度循环 v0：路由器和执行者组成 agent loop（2026-09-23）

补 `router-v0.md`、`supervisor-v0.md`。一句话：**路由器从「一次性分诊 + 几个零散介入点」变成一个任务从头到尾的调度 agent：规划 → 派发 → 看结果 → 决定下一步（再派 / 问用户 / 结束），直到做完。**

## 0. 为什么

现在一个任务里路由器被调用最多五次（分诊、重派、追问、代批审批、验收），每次都是互不相干的一问一答，它不记得上一次看到了什么，也不能主动「先派人去看看再决定」。典型失败：用户贴一行账号让录进平台，正确做法是先弄清平台表单要哪些字段、格式是什么，再按字段派人录入；现在只能一把梭，执行者拿着一坨东西自己猜。

## 1. 形态（推荐：代码驱动的步进循环）

- 每个任务给路由器开一个常驻 serve 会话，整个任务期间复用，它看得到自己之前每一步和每一步的结果（也吃得到 prompt cache）。
- 每一步路由器只回一个 JSON 动作，代码执行后把结果作为下一条消息喂回去：

| 动作 | 代码做什么 | 喂回给路由器 |
|---|---|---|
| `dispatch {harness, model, brief, needs_browser, purpose}` | 走现有全部底线：目录/额度/类别校验、审批策略、受保护路径、看门狗、线程/目录锁 | 结果全文（截断）、成败与失败类型、副作用计数、`out/` 文件、`git diff --stat` |
| `ask_user {questions}` | 现有问题卡片 | 用户答复，或「没答」 |
| `finish {completion, remaining, result, spoken}` | 根据完成程度终止；完整完成需验收，再写战绩、摘要 | — |
| `give_up {reason}` | 任务失败 | — |

- `purpose`：`research`（只看不改：审批一律拒绝写操作和表单提交，适合「去看看平台表单要什么字段」）、`do`、`verify`（只读复查）。
  > 2026-09-25 改：原来只读步骤里凡是要审批的一律拒绝，而 Claude 执行每条 shell 命令都要审批，「总结仓库最近的改动」连 `git log` 都跑不了（手机实测）。现在只读步骤里**只读的命令**直接放行（`executors/readOnly.ts`）：整行每条命令都在白名单里且只用于读（`git log/status/diff/show/rev-parse/ls-files/blame…`、只列不改的 `git branch/tag/remote/config --get/stash list`、`ls cat head tail wc grep rg find`（不带 `-exec/-delete`）、`ps lsof du stat` 等），没有写文件的重定向（`2>&1`、`>/dev/null` 除外）、没有命令/进程替换、没有后台、命令前不设变量、`git -c` 拒绝，且命令里的路径都在任务自己的目录里（手机任务要进别的目录只能靠登记的项目目录）。其余照旧拒绝；受保护路径的检查在它之前，不受影响。简报里写明哪些命令会放行。Codex 自带的沙箱（例如拦 `ps`）不在此列。
- 预算：每个任务最多派发 5 次、路由器最多 12 步，超出强制 `ask_user`「是否继续？」。
- 现有零散机制合并进循环：重派 = 路由器看到失败后再 `dispatch`；验收 = 路由器看到结果后决定 `finish` 还是再派；追问 = `ask_user`。额度耗尽换备选、传输错误重试一次仍由代码直接做，不打扰路由器。
- 简单任务不变慢：`dispatch` → `finish` 两次路由器调用，和现在的「分诊 + 验收」一样。

**不选的方案 A：路由器作为 opencode 里的工具调用 agent**（daemon 暴露 `dispatch / ask_user / finish` MCP 工具，由 opencode 自己跑循环）。好处是循环现成；坏处是一次 `dispatch` 可能阻塞 30 分钟，opencode 的工具调用超时和中断语义不可控，DeepSeek Flash 的工具调用稳定性也没验证过，而且测试只能打真模型。步进循环每一步都能用 echo 路由器脚本化测试。

## 2. 用户那个例子怎么走

1. 入口 sealer：`邮箱|密码|2024|United States|应用专用密码|session key` 按字段加密，带字段说明（`router-v0.md` §9，已实现）。
2. 路由器第 1 步：`dispatch purpose=research`，便宜的带浏览器模型：「打开平台 X 的添加账号页，列出每个字段的标签、是否必填、格式要求，不要提交」。
3. 喂回字段清单。第 2 步：`dispatch purpose=do`，简报里写明映射「Email ← 登录邮箱、Password ← 账号密码、Region ← United States（明文）……」。
4. 喂回结果。第 3 步：`finish`，或者先 `dispatch purpose=verify` 回去看一眼列表里有没有这条。

## 3. 边界（不变的）

- 路由器入口之后永远看不到明文；执行者的回显经 gate 替换回密文，喂回路由器也安全。
- 路由器仍然没有 shell 和写文件权限，一切动作经代码执行，代码底线不因为「路由器说可以」而放宽。
- 审批策略、`isSelfHarm` 硬拒绝、受保护路径快照恢复全部保留。

## 4. 已知限制

- 派生值做不了：平台要邮箱的前缀、要把密码拆两段，需要明文，而入口之后没有明文。要支持就得让 daemon 在任务期间把明文留在内存里（不落盘），由路由器用 `derive` 动作造新密文。v0 不做，除非用户要。
- v0 串行派发；要并行的仍然是拆成多个后台任务。

## 5. 用户决定（2026-09-23）

1. 形态：代码驱动的步进循环。
2. 模型：Flash 分诊；判断为多步任务时升级到规划模型接手整个循环。
3. 执行者中途提问：路由器先答，答不了再转给用户。

## 6. 实现细节（已实现，2026-09-23；`src/engine/taskLoop.ts`、`src/router/loop.ts`、`src/router/routers/claude.ts`）

实测（`scripts/planner_smoke.ts`，规划模型 claude-sonnet-5 经 Agent SDK 纯文本调用）：一条「把账号录进平台」的任务，第一步选了只读调研（去看表单有哪些字段、哪些必填、不要提交），喂回一份字段清单后第二步派发填表，简报里按字段名指代密文、把表单没有的字段明确排除。每步 13–18 秒，比 serve 上的 Flash 慢，因为要拉起一次 CLI。


**无状态转录，不持有会话。** 每一步把「任务 + 已走的每一步及结果」整段发给循环模型。原因：中途会从 Flash 换到规划模型，会话本来就接不上；echo 路由器也能逐步脚本化测试。上面 §1 说的「持有会话」作废。

**分诊字段。** 路由决策加两个字段：`plan: single | multi`、`purpose: research | do | verify`（默认 single / do）。Flash 判断 `multi`（要先看一眼再做、或有几步前后依赖）→ 规划模型从第一步起接手，Flash 的派发作废；规划调用失败或无有效动作时保留现场并阻塞，不重放先前派发。

**规划模型由路由器动态选（2026-09-23 用户决定）。** Flash 判 `multi` 时同时在决策里写 `planner: {harness, model}`：从目录里挑一个**做规划**的模型（不需要工具，只看每步结果决定下一步），步骤相互依赖、动作有风险、材料长就挑 top/high，简单的先看后做挑 mid，顺带看额度。代码校验这个选择（在目录里、额度够），不合格就退到 `targets.yaml` 的 `router.planner`（默认 `claude-sonnet-5`，只是兜底），再不行 Flash 自己跑循环。三家都能当规划模型：`claude-code` 走 Agent SDK 纯文本调用（`tools: []`、`maxTurns: 1`、不落会话），`codex` 走 app-server 的只读临时线程（用用户自己的 CODEX_HOME），`opencode` 走常驻 serve。实测 Flash 对「录入账号、表单未知」的任务判 multi 并选了 claude-sonnet-5 做规划；codex/gpt-5.5 当规划模型时同样先只读调研再填表，每步约 20 秒。

**每步之后谁来决定。**

| 这一步 | 结果 | 下一步由谁决定 |
|---|---|---|
| 任何 | 传输错误（第一次）/ 额度耗尽 | 仅已知无副作用时允许原样重试一次 / 沿备选链换目标；未知或已有副作用则停止 |
| 任何 | gate 拒绝 / 改了受保护文件 | 代码：直接失败（不变） |
| 任何 | 模型拒绝 | 独立诊断流程（router-v0 §6.2）：保留来源的事实澄清，最多一次同目标重试；有副作用、提供方安全拦截或诊断失败则停止，不走普通换模型/验收兜底 |
| 任何 | 其余失败 | 循环模型（原来的重派询问并入这里）；「批准过的动作之后失败」「有副作用的 task_failed」仍由代码停下交给用户（不变） |
| `do`，单步任务 | 成功 | 有监督者验收就验收（不变），通过即完成；不通过按失败交给循环模型 |
| `research` / `verify`，或多步任务 | 成功 | 循环模型：再派 / 问用户 / 完成 / 放弃 |

**动作格式。** 循环模型的回复兼容原来的派发格式：带 `harness` 且 `action` 是 `dispatch` / `redispatch` 的就是派发；另有 `{"action":"finish","completion":"complete|partial|blocked","remaining":[],"result":…}`、`{"action":"ask_user","question":…}`（`clarify` 同义）、`{"action":"give_up","reason":…}`。finish 的完成程度和剩余事项必填，完整完成必须有结果且无剩余事项。派发走原来的校验（目录、额度、类别、战绩护栏），失败过的目标排除。

**预算。** 一个任务最多派发 5 次、循环模型最多 12 步；到了就问用户「是否继续？」，允许则再给 5 次。

**只读步骤。** `research` / `verify` 派发时，简报前面加一句「只看不改、不提交任何表单」，执行者的审批请求一律拒绝（不问用户也不问监督者）。浏览器里点提交按钮这类不经审批的动作只能靠这句话约束，这是已知缺口。

**步骤之间的交接。** 每次派发的交接说明里带上之前每一步的目的、执行者、结果摘录，失败时再加原来的失败交接。多步任务完整完成时结果来自通过验收的 `finish.result`，不能用最后一次成功派发自动代替整项任务完成。

**执行者提问。** 先给监督者（路由器文本 agent）：只能用简报、用户原话、CONTEXT.md、之前的步骤作答；凭据只能用这些地方出现过的 `enc:v1:` 密文，出现任何不认识的密文就转给用户；拿不准就转。审批策略是 `manual` 时一律直接转给用户。答了的记事件 `supervisor {kind: question}`，时间线上看得到它替你答了什么。

**路由问题未答复时停止（2026-09-23）。** 首次分诊、循环路由器和规划模型提出的 `ask_user` / `clarify` 均须收到有效答复才可继续。用户点击拒绝、不答，或者问题超时，任务停止并保留待回答的问题；不得将缺答记录成可跳过的步骤，再调用模型决定后续派发。任务已被取消时保留取消状态，不额外改为失败。正常答复仍作为带来源的问题与答案交给后续调度。

## 7. 循环状态与重复操作修正（2026-09-23）

- `done` 仅表示目标完成；新增终态 `partial`（部分完成）和 `blocked`（等待补充条件），保留结果、阻塞原因及步骤检查点。预算耗尽、规划服务失效、验收未通过不能自动转换为成功。多步 finish 必须报告完成程度与剩余事项，并按原始用户目标验收；第二次验收失败也不能强制通过。
- 增加调度步数后先询问下一动作，绝不重新执行刚完成的派发。所有 await 返回后检查取消；取消及其它终态不可被迟到回调覆盖。
- 执行者提出的问题若未得到答复，立即中止本次执行并保存为 blocked，不将缺答包装成可继续的普通答案。已回答的有效输入正常继续。
- 副作用未知与副作用为零分开。异常保留已观察到的工具调用；浏览器、MCP 及子代理操作也计入可能副作用。只有可靠确认无副作用的传输错误才可原样重试；有副作用或未知时保存现场、停止自动重放，续跑先核对现场。
- 每次派发结束持久化步骤检查点：目的、执行结果、结果证据、可能副作用、需复查事项。检查点用于同线程续跑与摘要；不能作为再次执行或扩大授权的依据。
- 线程摘要与检查点提交完成前保留线程及目录锁；收尾必须有超时且 finally 释放锁。后续任务不能读取尚未提交的前序摘要，较旧摘要不能覆盖较新的进展。
- 取消后先等待执行器退出；适配器结束自己创建的进程组。超过收尾时限仍未退场的执行器登记为待退出，在它退出前阻塞相同线程或目录的新执行，并保留现场，不删除目录或相关任务。排队中未派发的取消任务不覆盖会话摘要。

## 8. 规划服务故障可观测性（2026-09-23）

- 分诊使用 `router.timeout_ms`；独立规划调用使用 `router.planner_timeout_ms`（默认 120 秒），包括启动模型和至多一次 JSON 格式纠正。不能沿用短分诊截止时间提前终止独立规划进程。
- 规划故障必须记录阶段、模型、错误类别、实际耗时和尝试次数；页面显示超时、服务故障或格式不合格的中文原因。诊断只记录固定类别和安全错误描述，不保存模型原始回复或原始提供方错误。
- 规划服务故障保持现场并停止；无执行步骤时明确显示尚未执行，不要求用户凭空补资料，不把故障当成授权或绕过模型拒绝，不自动重放业务步骤。

## 9. 沿用现有通路的反馈与纠错（2026-09-23）

不增加按业务场景分类的修复状态机。模型负责发现假设与现场的冲突，利用现有执行中提问和步骤结束后的规划通路反馈；代码负责答复有效性、来源记录、上下文传递、取消及续跑边界。

- 入口生成的字段名、布局、路由简报及历史摘要均包含模型推断，不能伪装成用户确认。用户陈述、现场观察和推断分别标识；现场有某个字段不证明输入值属于该字段。
- 执行者遇到会影响正确性的冲突，先暂停依赖该判断的动作，在现有提问工具中说明原假设、实际观察与证据、已完成操作、需要核对的结论。监督者可以依据材料纠正自己的假设；材料不足则用中文问用户含义或选择，不要求重新粘贴已有秘密。没有提问工具时，在步骤结果中明确报告未解决问题，交回循环规划。
- 监督者答复必须完整对应全部问题、非空、非错误来源、未要求转交，密文必须已属于当前任务；失败或超时转问题卡片，不能把空对象当成回答。每次等待有取消边界，结束后的迟到答复无效。
- `feedback` 事件保存问题、答复、答复者（用户或路由器）、状态和版本。事件序号是稳定来源引用。它是可追溯的问答记录，不通过额外模型调用将自然语言强行归并为永久事实。新答复针对同一问题明确纠正旧推断时，后续规划和执行采用新结论；路由器的推断不能覆盖用户明确陈述。
- 当前任务的反馈在下一次提问、下一轮规划、验收、后续派发中单独注入；相关前序任务反馈随交接保留，避免摘要遗漏或换模型后忘记纠正。用户答复仍是用户来源，路由器答复仍是生成内容；历史反馈不自动写入平台长期记忆。
- 不增加每步固定调用模型的开销。保留原检查点与副作用限制，不重放已完成操作，结果不明的写操作先只读核对。反馈不能改写原任务目标、扩大凭据权限、替代审批或绕过提供方拒绝；凭据修复仍走原有独立校验。

验证覆盖字段含义、文件路径及工具参数等不同场景，以及同会话多次提问、换模型、后续任务、无答复、无效代答、取消和超时；测试不调用真实模型或业务平台。
