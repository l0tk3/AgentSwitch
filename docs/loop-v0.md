# 调度循环 v0：路由器和执行者组成 agent loop（2026-09-23）

补 `router-v0.md`、`supervisor-v0.md`。一句话：**路由器从「一次性分诊 + 几个零散介入点」变成一个任务从头到尾的调度 agent：规划 → 派发 → 看结果 → 决定下一步（再派 / 问用户 / 结束），直到做完。**

## 0. 为什么

现在一个任务里路由器被调用最多五次（分诊、重派、追问、代批审批、验收），每次都是互不相干的一问一答，它不记得上一次看到了什么，也不能主动「先派人去看看再决定」。典型失败：用户贴一行账号让录进平台，正确做法是先弄清平台表单要哪些字段、格式是什么，再按字段派人录入；现在只能一把梭，执行者拿着一坨东西自己猜。

## 1. 形态（推荐：代码驱动的步进循环）

- 每个任务给路由器开一个常驻 serve 会话，整个任务期间复用，它看得到自己之前每一步和每一步的结果（也吃得到 prompt cache）。
- 每一步路由器只回一个 JSON 动作，代码执行后把结果作为下一条消息喂回去：

| 动作 | 代码做什么 | 喂回给路由器 |
|---|---|---|
| `dispatch {harness, model, brief, needs_browser, purpose}` | 走现有全部底线：目录/额度/类别校验、审批策略、受保护路径、看门狗、线程/目录锁 | 结果全文（截断）、成败与失败类型、副作用计数、`out/` 文件、`git diff --stat` |
| `ask_user {questions}` | 现有问题卡片 | 用户答复，或「没答」 |
| `finish {result, spoken}` | 任务完成、写战绩、摘要 | — |
| `give_up {reason}` | 任务失败 | — |

- `purpose`：`research`（只看不改：审批一律拒绝写操作和表单提交，适合「去看看平台表单要什么字段」）、`do`、`verify`（只读复查）。
- 预算：每个任务最多派发 5 次、路由器最多 12 步，超出强制 `ask_user`「还要继续吗」。
- 现有零散机制合并进循环：重派 = 路由器看到失败后再 `dispatch`；验收 = 路由器看到结果后决定 `finish` 还是再派；追问 = `ask_user`。额度耗尽换备选、传输错误重试一次仍由代码直接做，不打扰路由器。
- 简单任务不变慢：`dispatch` → `finish` 两次路由器调用，和现在的「分诊 + 验收」一样。

**不选的方案 A：路由器作为 opencode 里的工具调用 agent**（daemon 暴露 `dispatch / ask_user / finish` MCP 工具，由 opencode 自己跑循环）。好处是循环现成；坏处是一次 `dispatch` 可能阻塞 30 分钟，opencode 的工具调用超时和中断语义不可控，DeepSeek Flash 的工具调用稳定性也没验证过，而且测试只能打真模型。步进循环每一步都能用 echo 路由器脚本化测试。

## 2. 用户那个例子怎么走

1. 入口 sealer：`邮箱|密码|2024|United States|应用专用密码|session key` 按字段加密，带字段说明（`router-v0.md` §9，已实现）。
2. 路由器第 1 步：`dispatch purpose=research`，便宜的带浏览器模型：「打开平台 X 的添加账号页，列出每个字段的标签、是否必填、格式要求，不要提交」。
3. 喂回字段清单。第 2 步：`dispatch purpose=do`，简报里写明映射「Email ← 登录邮箱、Password ← 账号密码、Region ← United States（明文）……」。
4. 喂回结果。第 3 步：`finish`，或者先 `dispatch purpose=verify` 回去看一眼列表里有没有这条。

## 3. 边界（不变的）

- 路由器入口之后永远看不到明文；执行者的回显经 gate 替换回密文，喂回路由器也安全。
- 路由器仍然没有 shell 和写文件权限，一切动作经代码执行，代码底线不因为「路由器说可以」而放宽。
- 审批策略、`isSelfHarm` 硬拒绝、受保护路径快照恢复全部保留。

## 4. 已知限制

- 派生值做不了：平台要邮箱的前缀、要把密码拆两段，需要明文，而入口之后没有明文。要支持就得让 daemon 在任务期间把明文留在内存里（不落盘），由路由器用 `derive` 动作造新密文。v0 不做，除非用户要。
- v0 串行派发；要并行的仍然是拆成多个后台任务。

## 5. 用户决定（2026-09-23）

1. 形态：代码驱动的步进循环。
2. 模型：Flash 分诊；判断为多步任务时升级到规划模型接手整个循环。
3. 执行者中途提问：路由器先答，答不了再转给用户。

## 6. 实现细节（已实现，2026-09-23；`src/engine/taskLoop.ts`、`src/router/loop.ts`、`src/router/routers/claude.ts`）

实测（`scripts/planner_smoke.ts`，规划模型 claude-sonnet-5 经 Agent SDK 纯文本调用）：一条「把账号录进平台」的任务，第一步选了只读调研（去看表单有哪些字段、哪些必填、不要提交），喂回一份字段清单后第二步派发填表，简报里按字段名指代密文、把表单没有的字段明确排除。每步 13–18 秒，比 serve 上的 Flash 慢，因为要拉起一次 CLI。


**无状态转录，不持有会话。** 每一步把「任务 + 已走的每一步及结果」整段发给循环模型。原因：中途会从 Flash 换到规划模型，会话本来就接不上；echo 路由器也能逐步脚本化测试。上面 §1 说的「持有会话」作废。

**分诊字段。** 路由决策加两个字段：`plan: single | multi`、`purpose: research | do | verify`（默认 single / do）。Flash 判断 `multi`（要先看一眼再做、或有几步前后依赖）→ 规划模型从第一步起接手，Flash 的派发作废；规划模型出错或额度用完 → 退回 Flash 的决定。

**规划模型由路由器动态选（2026-09-23 用户决定）。** Flash 判 `multi` 时同时在决策里写 `planner: {harness, model}`：从目录里挑一个**做规划**的模型（不需要工具，只看每步结果决定下一步），步骤相互依赖、动作有风险、材料长就挑 top/high，简单的先看后做挑 mid，顺带看额度。代码校验这个选择（在目录里、额度够），不合格就退到 `targets.yaml` 的 `router.planner`（默认 `claude-sonnet-5`，只是兜底），再不行 Flash 自己跑循环。三家都能当规划模型：`claude-code` 走 Agent SDK 纯文本调用（`tools: []`、`maxTurns: 1`、不落会话），`codex` 走 app-server 的只读临时线程（用用户自己的 CODEX_HOME），`opencode` 走常驻 serve。实测 Flash 对「录入账号、表单未知」的任务判 multi 并选了 claude-sonnet-5 做规划；codex/gpt-5.5 当规划模型时同样先只读调研再填表，每步约 20 秒。

**每步之后谁来决定。**

| 这一步 | 结果 | 下一步由谁决定 |
|---|---|---|
| 任何 | 传输错误（第一次）/ 额度耗尽 | 代码：原样重试一次 / 沿备选链换目标（不变） |
| 任何 | gate 拒绝 / 改了受保护文件 | 代码：直接失败（不变） |
| 任何 | 其余失败 | 循环模型（原来的重派询问并入这里）；「批准过的动作之后失败」「有副作用的 task_failed」仍由代码停下交给用户（不变） |
| `do`，单步任务 | 成功 | 有监督者验收就验收（不变），通过即完成；不通过按失败交给循环模型 |
| `research` / `verify`，或多步任务 | 成功 | 循环模型：再派 / 问用户 / 完成 / 放弃 |

**动作格式。** 循环模型的回复兼容原来的决策格式：带 `harness` 且 `action` 是 `dispatch` / `redispatch` 的就是派发；另有 `{"action":"finish","result":…}`、`{"action":"ask_user","question":…}`（`clarify` 同义）、`{"action":"give_up","reason":…}`。派发走原来的校验（目录、额度、类别、战绩护栏），失败过的目标排除。

**预算。** 一个任务最多派发 5 次、循环模型最多 12 步；到了就问用户「还要继续吗」，允许则再给 5 次。

**只读步骤。** `research` / `verify` 派发时，简报前面加一句「只看不改、不提交任何表单」，执行者的审批请求一律拒绝（不问用户也不问监督者）。浏览器里点提交按钮这类不经审批的动作只能靠这句话约束，这是已知缺口。

**步骤之间的交接。** 每次派发的交接说明里带上之前每一步的目的、执行者、结果摘录，失败时再加原来的失败交接。完成时任务结果 = 循环模型 `finish.result`，没写就用最后一次成功派发的回复。

**执行者提问。** 先给监督者（路由器文本 agent）：只能用简报、用户原话、CONTEXT.md、之前的步骤作答；凭据只能用这些地方出现过的 `enc:v1:` 密文，出现任何不认识的密文就转给用户；拿不准就转。审批策略是 `manual` 时一律直接转给用户。答了的记事件 `supervisor {kind: question}`，时间线上看得到它替你答了什么。
