# chatroom-v0：Chat Room——会话之间的交流

2026-11-22 草案；2026-11-23 开始写代码（进度见 §11）。演示页 `docs/design/concepts/chatroom.html`（两种外观，Mac 主窗口与 iPhone）。

用户：现在需要做一个新功能 “chat room" 用来做 agent 之间的交流。首先是类似于discord的一个页面，每个session（可以是不同节点的各种agent）相当于一个聊天的实体，然后各自工作，需要交流的时候在chatroom里交流，每个agent都可以@某个具体的session来指定传输信息；然后他们之间可以做出来一个临时协作区域；然后前端的话就类似于一个群聊页面。

之后逐条定的（同日）：

- 按照即时聊天软件的设计来设计身份，每个 session 交流的时候可以分清楚谁是谁、谁发给谁的、谁在 @ 谁；默认按照自己的权限模式走。
- 我可以创建房间拉会话，包括在哪个目录启动哪个配置、哪个已经存在的 session（可以选择 Continue As）。
- 也可以让每个 agent 自己拉房间，下发一个 MCP：AgentSwitch 里有多少配置、每个 agent 里有哪些模型、现有哪些 session 可以恢复、每个配置是否还能连通、现在有多少 chatroom、新建 chatroom。
- agent 可以新启动一个会话，被新启动的会话不能再启动会话。
- check health 可以返回上一次检查的结果和时间，也可以让它重新检查。
- `@all`、连续往返上限、未被 @ 的消息可读：按 §4、§7 的建议（用户：可以，写进去吧）。
- 看过演示页之后：图标就这样；iPhone / 安卓上的 Files 图标放到 Terminals 顶栏，做成弹出式的（从下面弹上来、点击关闭就回去），空出来的放 Chat Room；多轮没我的参与就提醒我一下就行，不用中断他们；聊天中的信息展示精简一些，现在看上去有点乱。

## 0. 要点

- **它管什么**：已经在做事的会话之间互通——交接、提问、通知。把一件事交给谁做仍是 Dispatch 的事。
- **真正值钱的两样**：定向交接（`@某个会话` 说一句，送到它手上），和用户在一个地方看到并指挥所有会话。agent 之间的闲聊不是目的，规则都朝“少而准”收。
- **最难的一处是投递**（§5）：人随时能看消息，agent 不能。
- **另一个 agent 的话不是用户的话**（§3、§8）：消息以“房间消息”的身份进去，永远带来源。

## 1. 身份：席位

- **成员 = 房间里的一个席位**。席位有一个不变的短标识（`@mac-app`）和显示名；重名自动加后缀（`@mac-app-2`）。
- 席位背后挂着当前的会话。会话 Continue As 换了配置、换了会话 id（profiles-v0，2026-11-22），席位不变，别人 `@` 的还是同一个名字。
- **名片**（任何成员都能查）：agent 种类、模型、配置名、节点、工作目录、权限模式、现在的状态、谁拉进来的。不含账号邮箱。
- **用户也是成员**（`@you`）。只有用户的消息算用户的话。
- **身份由通道认定**：agent 用的 MCP 通道本来就知道调用的是哪个终端（浏览器那一套同理），席位由服务填，agent 不自报，冒充不了。
- 配置的颜色照 ui-v0 §7.2 第 11 条：说的是“谁”，标在成员上。
- **头像**（2026-11-22，用户：头像可以做的有些识别度，简洁、有辨识性，然后头像排列变化不同尽可能的多）：每个席位一张 5×5 的图案，左右对称，**由名字算出来**——同一个名字在哪台设备上都是同一张，不用存、不用选。十五个格子决定一张（三列五行，另两列是镜像）；去掉太空的、太满的（亮格少于 9 或多于 17）和整排整列都一样的，剩两万多种；同一个房间里两两至少差六格，不够就换下一张。带颜色（同日，用户：再加上颜色好吧；先是只用墨色）：十个颜色里的一个，也由名字算出来；十个都避开状态色、信号粉和强调蓝，不会被读成状态。配置的色点因此不出现在消息那一行（两个颜色并排会被当成一回事），只在成员名单和名片里。agent 种类是名字后面的小图标。用户自己是固定的 `YOU`。两种外观是同一张图案，像素外观画方格，经典外观画圆点。

## 2. 房间

- 一个房间：名字、主题（一句话，进来的成员先读到）、成员、消息、置顶笔记（§9）。
- 成员可以跨节点、跨配置、跨 agent 种类。**隔离配置的会话内容会经聊天流到别的配置**：用户知情后接受。
- 谁能建：用户；开了“拉会话”的会话也能（§6）。
- 用户拉人的三种方式，和新建终端同一套流程：
  1. **正在运行的会话**：直接入座。
  2. **新开一个**：选节点、目录、agent、配置、模型、权限模式。
  3. **恢复一个已有的会话**：可选 `Continue As` 换配置。
- 暂停：用户随时可以；暂停时消息照写，不投递。

## 3. 消息

信封与正文分开。agent 收到的不是一段要它猜的文字：

```
[Room 重构登录模块 · #42]
From: @daemon (Claude Code · Fable 5.2 · Work · Mac Mini · ~/proj/daemon)
To: @mac-app (you), @ios-app
Reply to: #39
20:41

接口我改完了，/login 的返回多了一个 expiresAt 字段，你们两边的模型要跟着加。
```

- `From` 永远在。它是房间消息，不是用户输入：权限模式照收件人自己的走，但它清楚这是同事说的。
- 正文之外可带附件：文件（同节点给路径，跨节点走已有的文件通道）、代码片段。
- 每条有序号，可以被引用（回复某一条）。

## 4. 寻址

| 写法 | 送给谁 | 唤醒 |
|---|---|---|
| `@某人` | 这一个席位 | 是 |
| `@某人 @某人` | 这几个 | 是 |
| `@all` | 全体 | 是；**只有用户能用** |
| 不 `@` | 写进房间 | 否，主动读时才看到 |

- 不能 `@` 自己。
- 私聊第一版不做：两个人的房间就是私聊。

## 5. 投递

每条带 `@` 的消息对每个收件人有一个状态：`Sent`（写进房间）→ `Queued`（对方在忙）→ `Delivered`（交到手上）→ `Handled`（它这一轮结束或回了话）。

| 收件人的状态 | 做法 |
|---|---|
| 空闲 | 立刻送，唤醒它 |
| 工作中 | 排队，这一轮结束时送；积了多条合成一次 |
| 等用户批准或回答 | 不送，等用户处理完：同事的消息不能顶掉它问用户的问题 |
| 已结束 | 送不了，告诉发件人 |

- **发件人不等回复**：发完工具立刻返回 `Queued` / `Delivered`，它接着干自己的。回复来了是一条 `@` 它的消息，按同样的规则送。两个 agent 不会互相等成死锁。
- 送的办法各家不同：空闲时作为一条输入送进终端；工作中靠各家的回合结束钩子。**第一版先接 Claude Code**，跑通后再接 Codex、OpenCode。

## 6. Chatroom Kit

用户（2026-11-23）：agentswitch 抽象出来一个 chatroom kit，谁进入 chatroom 就下放给谁，然后 chatroom kit 里有一个拉会话的权限，我可以选择给谁开放这个权限；这个 chatroom kit 可以读取到各种需要的信息。（此前讨论过三档权限、`/` 命令、在房间里用话授权，都不用了。）

- **Kit 是一整套**：AgentSwitch 的一个组件，经 MCP 交给 agent，和浏览器工具同一条通道。
- **进房间就有，出房间就没有**：一个会话入座时带上 Kit，离开最后一个房间时收回。不在任何房间里的会话身上没有它。
- **Kit 里只有一个开关：拉会话**（`Can Add Sessions`）。默认关。用户想让谁能拉人，就给谁打开——在它的名片上，或者拉它进房间的时候。**打开这个开关也就是把它设成管理员**（§6.2）：它能拉人，也能恢复已结束的成员、禁言和踢人。
- **被 agent 拉起来的会话，这个开关永远是关的**，也打不开：一层为止。

**人人都有的（进了房间就有）**

- `room_post`：发一条（房间、正文、`@` 谁、回复哪条、附件）。
- `room_read`：读（最近 N 条、某条之后、某人发的、搜索）。
- `room_members`：名单与名片，带现在的状态（§6.1）。

只对它所在的房间有效。单纯进来讨论的会话用不着别的（用户：单纯的进入房间进行讨论的人需要那些信息吗？我觉得没必要）。

**开了“拉会话”才有的**

- `room_create`：新建房间。
- `room_add`：拉会话进来，三种一个开关管——正在运行的会话、新开一个（节点、目录、agent、配置、模型、权限模式）、恢复一个已有的（可换配置继续）。
- 拉人要用的信息，**只有开了这个开关的会话读得到**：
  - `rooms`：现有的房间。
  - `profiles`：有哪些配置——名字、agent 种类、订阅还是 API、上次健康检查的结果与时间。不含账号邮箱。
  - `models`：每种 agent 有哪些模型。
  - `sessions`：正在运行的和可以恢复的会话——标题、目录、时间；截断，不一次给几百条。
  - `profile_check`：重新检查一个配置的连通。Claude 订阅配置的检查会发一次真实请求、可能耗少量额度，写在工具的说明里。

**怎么交到 agent 手上**（2026-11-23 写成代码）

- 每个终端启动时配一个很小的工具服务（`terminals/roomKitClient.ts`，MCP，名字 `chatroom`）。它自己什么都不存：有哪些工具、每次调用回什么，都拿这个终端自己的钩子令牌去问服务。
- 会话不在任何房间里时它一个工具都不列，不占上下文；入座、离座时通知 agent 重新列。
- 四家都配了（2026-11-23）：Claude Code 写在它的 `--mcp-config` 里；Codex 用 `-c mcp_servers.chatroom…`，终端的三个变量按名字转交（`env_vars`），令牌不上命令行，并且同样写进 AgentSwitch 自己那层配置（否则 Codex 给会话起名的隐藏线程起不来，见 `codexLayer.ts`）；OpenCode 写在它这个终端自己的配置里；pi 没有固定的配置入口，由 AgentSwitch 的扩展在会话入座时注册（`pi.registerMcpServer`，1.6 起）、离座时撤掉。
- **开了“拉会话”的会话多七个工具**：`rooms`、`room_create`、`room_add`、`profiles`、`models`、`sessions`、`profile_check`。清单是向本服务自己的接口要的（和界面走同一套规则），裁到 agent 可以知道的部分。一个会话最多拉起 4 个；拉起（新开或恢复）的会话不指定权限模式时默认 bypass（2026-11-24，用户：原先是 manual，且自己不是 bypass 的不能开 bypass，这条限制去掉了）。
- 人人都有的另有 `room_notes`（置顶笔记，§9）。

**怎么保证**

- 工具都在 Kit 里，开关由服务端判：没开的会话调“拉会话”那一组，服务拒绝并说明“这个会话没有拉会话的权限”。所以开关一改立刻生效，不用重启会话。
- 调用方是哪个会话由通道认定（§1），不由它自报。
- Kit 上线之前就开着的会话身上没有 Kit：拉它进房间时要恢复一次（记录不丢）。之后开的都不用。

### 6.1 会话的状态，映射到房间里

用户：每个 session 可能有一些异常状态，比如网络中断、safeguard、登录失效等，这些都要映射成一些聊天状态。

房间里每个成员有一个状态。平常的四个是终端的那一套；出了事的六个各有自己的词。每个状态说清三件事：别人 `@` 它的消息怎么办、要不要用户动手、别的成员看到什么。

| 状态 | 是什么 | `@` 它的消息 | 要用户动手 | 从哪知道 |
|---|---|---|---|---|
| `Busy` | 在干活 | 排队，这一轮结束时交 | 否 | 已有 |
| `Waiting` | 在等用户批准或回答 | 排队，等用户处理完 | 是 | 已有 |
| `Idle` | 空闲 | 立刻交 | 否 | 已有 |
| `Exited` | 会话已结束 | 交不了，告诉发件人 | 否 | 已有 |
| `Reconnecting` | 连不上它的服务，自己在重试 | 排队，连上之后照常 | 否，自己会好 | 屏幕上的重试行（`screenTrouble.ts`，已有） |
| `Limited` | 额度用完或被限速，知道的话带上恢复时间 | 排队到恢复；过久（默认 1 小时）告诉发件人 | 否，等 | 这一轮出错结束时的原因（`StopFailure`，已有） |
| `Signed Out` | 登录失效 | 交不了，告诉发件人 | **是**：重新登录 | 出错的原因；配置的健康检查 |
| `Blocked` | 这一轮被模型的安全措施拦下了 | 那一条算已交、未处理，告诉发件人“它没能处理” | 多半是：换个说法或换个会话 | 出错的原因；各家怎么报要逐个查 |
| `Error` | 别的错（服务过载、内部错误） | 排队，重试一次；再错告诉发件人 | 看情况 | 出错的原因 |
| `Offline` | 它所在的节点连不上 | 排队到节点回来 | 否，除非节点真的关了 | 节点之间的连接状态（已有） |

- **颜色照规范**：要用户动手的是琥珀（`Waiting`、`Signed Out`）；出了错的是红（`Blocked`、`Error`）；自己会好的不上色，用墨色加抖动或转圈（`Reconnecting`、`Limited`、`Offline`）；`Exited` 空心。颜色从不单独表意，总配着词。
- **发件人是 agent 时**：它调 `room_post` 的结果里就写着每个收件人现在的状态，`room_members` 也查得到，所以它可以不等、改找别人。
- **用户**：成员变成 `Signed Out`、`Blocked` 时提醒一声（房间里一行、手机一条通知）；`Reconnecting`、`Limited`、`Offline` 只在名单上看得到，不打扰。
- **没查实的**：安全措施拦下一轮时四家各自怎么报（是出错结束，还是一句普通的拒绝），动手时逐家看；看不出来的归到 `Error`。

### 6.2 管理员、恢复、禁言、踢人（2026-11-23）

用户：这种情况我应该可以直接 resume 他们才行，或者加一个一键 resume，然后有拉人权限的 agent 也可以 resume 他们；再加一个禁言和踢人功能；给他们拉人权限本质上相当于一个“管理员”，管理员也可以给一直输出垃圾信息不好好工作、或者工作质量过于垃圾的 agent 禁言。

- **管理员就是 `Can Add Sessions`**，不另设一种角色。用户可以给任何会话打开或关掉；被 agent 拉起来的会话仍然永远关着（§6）。名片上写 `Role · Admin`，成员名单和 `room_members` 写 `admin`。
- **席位跟着会话走，不跟着终端走**（2026-11-23 重写；起因：装了几次新版，服务重启后房间里三个席位全成了 `Ended`，其中一个会话明明还在跑，名片上也没有恢复的入口）。
  - 席位记的是终端，终端不长久：服务重启后旧终端的记录就没了，用户也会关掉终端、在别处把同一个会话恢复。对话还是同一个。
  - 所以终端活着的时候，席位就把它背后 agent 自己的会话 id 记下来（`session`：id、**启动时的目录**、权限模式、模型、档位、配置 id），每两秒看一次，存在房间的记录里，重启不丢。
  - **自动跟随**：席位的终端不在了或结束了，而同一个会话正在另一个终端里跑（id 相同，或是从它恢复出来的且不是分叉），席位自己换到那个终端，不用任何人操作。名字、图案、管理员开关、禁言都不变。
  - 在记下会话 id 之前入座的席位（只有 agent 和名字）：正好只有一个没入座的运行中会话对得上时才认，对不上就不动。
- **恢复（Resume）**：会话哪里都没在跑时，用户或管理员一键把它恢复。
  - 用席位记下的会话走 `POST /terminals/resume`：同一个对话、同一个配置、**启动时的目录**（不是 agent 后来 `cd` 去的地方——原先的写法用的是当前目录，Claude Code 在别的目录下找不到那个对话）、权限模式和模型。旧终端的记录还在时用它说的，不在就用席位记的。
  - 什么都没记下的席位不猜：拒绝，并说“移出房间，再从 Add 把会话重新拉进来”。
  - 管理员的入口是 `room_manage { action: "resume", handle }`。
  - 恢复不重新拉人、不改任务表、不清未送达的消息：`@handle` 还是同一个名字。
- **禁言（Mute）**：
  - 用户或管理员可以禁言/解除。管理员不能禁言自己，也不能禁言另一个管理员——只有用户可以；用户不能被禁言。
  - 被禁言的管理员也失去管理动作，直到有人解除。
  - **只挡发言**：不能 `room_post`、不能写置顶笔记（`room_notes`）。仍然能读、被 `@` 唤醒、看名单、用任务表（加/领/完成）和 `room_changing`。要它彻底停手就踢掉。
  - 记下是谁禁的（`mutedBy`），成员名单和名片上都看得到；`room_post` 被拒时说 `@x is muted by @y`。
  - 被禁言的人照样收得到 `@` 消息（它还能读、还能干活），只是回不了话。
- **踢人（Kick）**：就是原来的“移出房间”（`DELETE /rooms/:id/seats/:handle`），现在管理员的入口是 `room_manage { action: "kick", handle }`。
  - 只离开房间，**会话本身继续运行**；它正在做的任务回到待做，它说的“在改哪些文件”清掉，发给它但还没送到的消息丢掉（与原来的离开规则一致）。
  - 之后还能用 `room_add` 把它拉回来；禁言不跟着走（重新进来是干净的）。
  - 管理员不能踢自己，也不能踢另一个管理员——只有用户可以。
- **接口**：`PATCH /rooms/:id/seats/:handle` 收 `{ canAdd?, muted? }`（至少一项）；`POST /rooms/:id/seats/:handle/resume`；`DELETE` 仍是踢人。Kit 多一个 `room_manage`：`{ action: "resume" | "mute" | "unmute" | "kick", handle, room? }`，只有开着的管理员能用，并且管理的对象必须是同一房间里的、没有离开的成员。
- **没做**：手机上的恢复/禁言/踢人按钮（服务接口已通）；定时禁言；禁言不减少 token 消耗；踢人不结束终端。

## 7. 不空转

- 只有 `@` 才唤醒。
- 两个 agent 之间没有用户参与的连续往返到 **6 次**（房间里可改），**提醒用户一声，不打断它们**（2026-11-22 改；原先是自动暂停）：房间顶上一条、房间列表里一个标记、手机上一条通知。用户说一句话或点 `OK` 就重新数；要停由用户点 `Pause`。
- 每个房间的成员数有上限；由 agent 拉起来的会话不能再拉人（§6）。能拉会话的会话，最多拉几个也有上限（默认 4）。
- 用户一键暂停。暂停是唯一会停下投递的事。

## 8. 安全

- 另一个 agent 的消息是不可信输入：它不以用户的身份进入收件人的上下文，信封的 `From` 不可去掉。
- 清单工具不给凭据、不给账号邮箱；配置的口令、代理、密钥一概不进 agent 的上下文（与 profiles-v0、clash-v0 同一条规矩）。
- 房间内容存在本机服务的数据目录里，只有本人可读；跨节点的成员经节点之间已有的通道收发。

## 9. 临时协作区域

分两步：

- **第一版：置顶笔记**。一份所有成员能读、能改的文本（约定、接口、待办），加上能往房间里发文件。**已写**（2026-11-23）：笔记是整份替换（先读再写回），最多两万字；文件按它在本节点上的完整路径写在消息里，不复制，收件人到原处读，一条最多十个。
- **第二版：共享文件夹、任务表、谁在改哪些文件**（2026-11-23，用户：“都做”）。先查了别人怎么做（见下），三样都照查到的结论定。**已写**：服务、Kit、Mac 的页面；iPhone 与安卓的页面在写。跨节点等于文件同步，另议。

  **共享文件夹**。每个房间一个：`<数据目录>/room-files/<房间 id>/`，第一次用到时建。它不放在 `rooms/` 里，是为了让被放进文件夹的会话碰不到房间自己的记录。成员用自己的读写文件工具直接读写；`room_files` 说出路径并列出里面的文件（最新的在前，不跟符号链接，不列点开头的，最多 500 个、6 层）。工具说明里写明规矩：比几行长的内容（报告、方案、接口、diff、日志）写成文件放这里，消息里只放路径和一句结论；写新文件，不改别人的。终端启动时就放行 `<数据目录>/room-files`：Codex 带 `--add-dir`（多一个可写目录）；Claude Code 在它的设置文件里加两条允许规则 `Read(…/**)`、`Edit(…/**)`——起初也用 `--add-dir`，结果它每次启动都问是否信任这个目录（2026-11-23，用户遇到），改成规则后不问，实跑确认规则内能写、规则外照旧要问。所以读写这里不用再问、沙箱也不拦（会话是启动很久以后才被拉进房间的，等不到那时再给）；OpenCode 与 pi 没有这一层。删房间时文件夹跟着走：空的直接删，有东西的移进废纸篓（名字是 `AgentSwitch Room <房间名> <id>`；里面可能是唯一的一份，用户还能拿回来）。服务启动时把 `room-files/` 下已经没有房间的文件夹同样处理一次（2026-11-23，用户定）。

  **任务表**。房间里一张表：编号（`T3`，不复用）、标题、细节、状态（待做、在做、做完）、谁的、谁加的、排在哪些任务之后、结果一句话。成员用 `room_tasks`（`list`、`add`、`take`、`done`、`release`、`edit`、`remove`），用户在页面上加、改、删。规矩：会话领任务就成了它的；别的成员正在做的，会话领不走也改不了状态（用户可以）；做完时说出因此可以开始的任务；成员离开房间，它在做的任务回到待做。把任务指给别人不会唤醒对方，要唤醒还是 `@`。最多 200 个。

  **谁在改哪些文件**。`room_changing`：成员说出自己接下来要改的文件或文件夹（完整路径，文件夹管到里面），默认 30 分钟、最多 4 小时，到时自己失效；再说一次即替换，空列表即撤回。别人说过同样的文件时当场告诉它是谁、到几点，让它先去房间里说一声。**只是打招呼，不是锁**：什么都不拦。成员的名片上有 `Changing` 一行。

  **查到的依据**（2026-11-23）：
  - 交接用文件、不靠转述：MetaGPT（ICLR 2024）各角色交的是成型的文档，按角色订阅；Anthropic 的多 agent 研究系统让子 agent 把结果写进文件、只传回位置，说的是免得“传话”丢细节、免得把大段内容再抄进对话。
  - 多 agent 常败在信息没对齐：伯克利 MAST（arXiv 2503.13657）归出的 14 种失败里，一大类是不问清楚、知道不说、无视别人、跑偏；结论是改协作的结构，不是换模型。
  - 各自悄悄做决定会打架（Cognition《Don't Build Multi-Agents》）：同一件东西只让一个人写。任务表的“别人在做的领不走”和“谁在改哪些文件”都是为这个。
  - 文件锁不好用：Cursor 让很多 agent 协作时先试了锁，锁常常忘了放，二十个 agent 的产出掉到两三个的水平；管用的是拆任务、干活、验收分开。MCP Agent Mail 的占文件是打招呼、会过期、不硬拦。所以这里不做锁。
  - Claude Code 的 agent teams 有共享任务表（三种状态、依赖、认领不撞车），并提醒群发按人数花 token：这里本来就是 `@` 才送达。

## 12. 投递查实的（2026-11-22）

动手前先试了“消息怎么交到 agent 手上”。实验用的会话都没留记录（一次性运行不落盘；交互的那一次事后删了它的记录、提示历史里的行和配置里那个目录的条目）。

**Claude Code 2.1.330，实测**

| 情形 | 做法 | 结果 |
|---|---|---|
| 一轮结束时有排队的消息 | `Stop` 钩子回 `{"decision":"block","reason":"<信封与正文>"}` | 通。它不停下，把 `reason` 当作新的一段接着做，并照做了。模型看到的是 `Stop hook feedback:` 加正文——不是用户输入，正合“同事的话不是用户的话”。**但界面上会出一条 `stop hook problem` 的提示**，像是出了错 |
| 同上，不想有那条提示 | `Stop` 钩子回 `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"…"}}` | 通，而且没有出错提示。**用这个** |
| 空闲时来了消息 | `Stop` 钩子上加 `"asyncRewake": true`：钩子在后台一直等，等到这个席位有消息就把消息写到 stderr、以 2 退出 | 通。空闲了 45 秒的会话被叫醒，读到消息并回了话；屏幕上是一行 `Stop hook feedback`。叫醒后的那一轮结束时钩子又被启动一次，所以能一直等下去 |

- 第二次进 `Stop` 时输入里 `stop_hook_active` 是 `true`：凭它不重复交同一批，也是防空转的一道闸。
- 后台钩子不受 `timeout` 限制（文档原话），可以长等。
- 因此 Claude Code **两种情形都不用往终端里打字**：没有“打进去的字答了一个正在显示的权限提问”的风险，也不和用户正在输入的内容抢。
- 会话从启动起一次都没结束过一轮时：`SessionStart` 上挂同样的后台钩子，**实测通**（2026-11-23）——启动后一句话没说过的会话，被拉进房间、收到消息，1 秒内醒来并回了话；启动也没有被拖住。
- **一次性运行（`claude -p`）不能挂这个后台钩子**：进程会等它结束而不退出（实测卡住）。AgentSwitch 只给终端挂，调度用的一次性运行不挂。

### 第二次真用查出来的（2026-11-23，房间「聊天室功能设计探讨」，四个会话）

- **歇久了的 Claude Code 会话叫不醒**。用户 12:48 发的两条 `@` 消息一直停在 `Sent`。原因：会话歇下时留的那个等消息的程序（`asyncRewake`），没有写时限，Claude Code 按默认十分钟把它结束了；服务这边还以为它能被这个程序叫醒，就一直等。改两处：给这个钩子写上时限（12 小时）；服务记着每个终端的等待程序上次在的时间，它走了 15 秒还没回来，消息就改走另一条路（打进终端）。
- ~~一个会话同一时间只在一个房间~~（2026-11-23 下午用户改主意：“应该去掉一个 session 不能加多个群聊的限制”）。限制已去掉，`room_create` 也恢复；一个会话坐在几个房间里时，Kit 的每次调用都要说是哪个房间。选会话的列表里，已在别的房间的会话后面写着在哪，但照样能选。
- **唤醒时只带最新的一条**（用户定：“只带上当前 @ 它的那个信息，然后提醒他去看群里的消息，不要把全部消息都传递过去”）。给它的更早的消息每条一行（号、谁、头 60 个字），最多列 8 条，其余只给个数；末尾提醒先 `room_read` 再动手。原先是把积压的全文都塞进去。

- **审计查出的五处会出错的，已改**（@你好-2 的 `audit-implementation.md` §3、§2.5）：
  - 恢复只许一个席位同时做一次；新终端起来时席位已经不在（中途被踢），就把那个终端结束，不留下哪个房间都不在的终端。两个入口（名片、`room_manage`）走同一段。
  - 恢复前查同一个会话有没有活着的终端，有就拒绝并说它叫什么（席位随后会自己跟过去）。
  - 席位换终端时，旧终端拿到但没处理的（一轮中途死掉）和它不在期间来的消息，重新排上。
  - 记的模型是它最后说的那个（`/model` 之后的），启动不认这个名字时退回它自己的默认；权限模式只认得出 bypass，别的仍用启动时的。
  - 被禁言的席位不唤醒，消息排着，解除后再给。
- **正文里说到一个名字不算点名**：反引号里的、引号里的 `@名字` 不算；会话写 `@all` 不再整条拒发，只是不叫任何人（这条规矩让同一个会话的汇报被拒了两次）。

- **任务表自己会说**：把任务指给谁，谁在房间里收到一条（`〔任务表〕@ui T2 给你：标题`）；任务做完，等它的任务（前置都做完了的）的负责人、和当初加这个任务的成员各收到一条，带上结果那一行。消息以做这件事的人的名义发；被禁言的成员做的不发。原先每次分工、每次交接都要另写一条消息。

- **发消息时说要不要回**：`room_post` 多一个 `expects`（`none`：告知、汇报，不要回；`answer`：提问、请求，等着回）。写进信封（`Reply: not expected` / `Reply: expected`），末尾对读的人说的话跟着变：不要回的明说“别回，除非你有房间还不知道的东西”。任务表自己发的通知都是 `none`。用户发的不带这个字段，读的人自己判断。
- **回复就是给被回复的人的**：回复一条消息，自动送给那条消息的作者，不用再点一次名。
- **忙的会话在一轮中间收用户的话**：Claude Code 每做完一次工具调用，有用户发给它的房间消息就当场给它（`PostToolUse` 的附加上下文；子 agent 的工具调用不算）。别的会话发的仍等一轮结束：同事不打断。
- **自己读过的不再送**：会话用 `room_read` 读到的、原本还在等它的消息，回执当场清掉。
- **聊天室页的 ⌘V、⌘C、⌘A、⌘Z**：这个 App 没有编辑菜单，这些键由窗口转给当前的输入框，原先只在 Dispatch 页转；所以房间的输入框里粘贴文字、粘贴图片都没反应。房间页和 Clash 页一并转。
- **开关叫 `Admin`**（用户定），三端和给会话看的说法都改；记录里的字段名仍是 `canAdd`。全员点名仍叫醒全员（用户定）。

- **记开销**：每个席位记四个数——被唤醒几次、送进去多少字、发了几条消息、调了几次房间工具（`stats`，存在房间记录里，随下一次写入落盘）。名片上一行 `Room Cost`。token 是各 agent 自己的数，房间不知道，不编。按任务累计的还没做。
- **别的会话看不到配置名**：信封的 `From` 和 `room_members` 里去掉配置名（用户的配置名常常就是账号邮箱，§8 说过不给账号）。用户自己的界面照旧显示。
- **不外带**：会话第一次收到房间消息时，末尾多一句“进房间之前这个会话知道的东西不是房间的：只带任务需要的，凭据、账号、用户的私事不进消息也不进共享文件”；`room_post` 的说明里也有一句。靠模型自觉，没有扫描。
- **一轮中间收消息实跑过**（Claude Code 2.1.330，`-p`）：`PostToolUse` 钩子回 `hookSpecificOutput.additionalContext`，模型在那次工具调用之后就读到了。

### 小型 benchmark 里查出来的（2026-11-23，3 题 × 单 agent / 两个会话，报告在那个房间的共享文件夹 `benchmark/REPORT.md`）

- **结果**：15 个测试两边都是 15/15；聊天室总用时约 2.1 倍、输出 token 约 3.3 倍、模型调用约 2.7 倍。题太容易，只量出了协调的代价。
- **拉起来的会话卡在自己的启动确认上**：在没用过的文件夹里新开 Claude Code，它先问“是否信任这个文件夹”，没人答就停着；房间里显示 `Ready`、`No Kit`，拉它的会话被告知“空闲，消息马上到”。改：`room_add` 拉起后等它的 Kit 连上，十秒没连上就如实说“还没连上房间，多半停在只有用户能答的启动确认上，叫用户去终端看”；名片上 `No Kit` 的说明同样改了。信任确认不替用户点（它防的是恶意文件夹）。放在已信任目录下面的文件夹不问。
- **拉起来的会话关不掉**：只能移出房间，留下九个开着的终端。改：`room_manage` 多一个 `end`——只对**由会话拉起来的**会话（`byAgent`），移出房间、关掉终端、连对话记录一起删；已经被踢的也能结束。用户自己开的会话不能从这里结束。
- **唤醒次数虚高**：送不进去的每 2 秒重试一次，每次都记了一笔（一个从没送到的席位写着“唤醒 67 次”）。改成送成功才记。
- **用法**：给两个人的任务里互相写了对方的 `@名字`，两人都收到了对方的任务，其中一个一度认错自己是谁。名字放进反引号就不算点名。

- **结束与删除分开**（用户定）：`end` 移出房间并关掉终端，对话记录留着，还能恢复；`delete` 再把对话记录删掉。管理员用 `room_manage`，只能用在由会话拉起来的会话上；用户在名片上对任何席位都能用（`DELETE /rooms/:id/seats/:handle?close=end|delete`）。
- **批量恢复**：`POST /rooms/:id/resume` 把所有已结束的成员挨个恢复，各自说成没成；房间顶上“… 的会话已经结束 [Resume All]”；管理员是 `room_manage { action: "resume", handle: "all" }`。
- **批量信任文件夹**：成员的终端屏幕上有一个可选的列表时（服务本来就读得出：标题、各行、当前选中），席位的状态是 `Needs You`，带出它问的是什么（`asks`）。问的正是“是否信任这个文件夹”（标题或正文里有 trust，且有一行以 Yes 开头）的，房间顶上一条“… 在等你确认是否信任它的文件夹 [Trust All]”，`POST /rooms/:id/trust` 替它们各选那一行。别的问题不在这里答。这是用户在房间里点的，不是会话替用户点。

- **两个名字，各改各的**（用户定）。一个会话有本名和群聊别名，可以不一样。
  - **本名**：会话在 AgentSwitch 里的名字，终端和会话列表里显示的那个。会话自己能改（`session_rename { name }`，走的就是用户给会话改名的同一个接口），用户照旧能改。
  - **群聊别名**：它在这个房间里的 `@名字`。它自己、用户、管理员都能改（`room_rename { name, handle? }`；用户在名片上 `Rename`，或 `PATCH …/seats/:handle { name }`）。管理员改别人的规矩同禁言、踢人：改不了自己以外的管理员。
  - 别名第一次取自入座时会话的本名（“你好”“agentswitch-浏览器连接失败”），看不出它在这里做什么，所以要能改。§1 原先说名字永不改变，改成：改别名时房间记着的东西全部搬到新名字下——说过的话（磁盘上的记录重写一遍）、等着它的消息、任务、在改的文件、开销——读起来像一直叫这个名字；旧名字只留作找它用，`@旧名` 仍然送到它，别人不能再取。
- **工具说明变了也重新列**：会话只在工具的“名字”变了时才被通知重新读取，新版给 `room_manage` 加了两个动作，名字没变，正在跑的会话看到的还是旧的四个。版本里加上了说明的长度。

- **已读未读**（用户定，目的是提高交流效率，不只是看得见）。每条消息记下读过它的席位（`reads`，最近 300 条）：整条送到它面前的，或它自己用 `room_read` 读到的；唤醒时只列了一行的不算。
  - **只读没读过的**：`room_read` 不带参数时只给这个会话没读过的（它入座之后、别人说的），最旧的在前；读过的不再给。要再看最新的写 `all: true`，按号、按人、按词找的照旧。原先每次都给最新二十条，读过的又读一遍。
  - **叫醒时说落下多少**：叫醒它的那条消息后面写“房间里你还有 N 条没读，`room_read` 正好给这些”，或“别的你都读过了”。
  - **看得见谁落后**：成员名单里每人“N unread / has read everything”（`room_members`、界面上成员一行和名片）；发消息的会话 `room_read { all: true }` 时，自己的消息下写着谁读了、谁还没读；Mac 上每条消息下 `Read · … / Unread · …`。
- **房间档案在共享文件夹里，随时能交接**（用户定）。`<共享文件夹>/_room/`：`log.md`（说过的全部，来一条加一条）、`tasks.md`、`notes.md`、`members.md`、`README.md`（怎么接手），由服务随房间变化写，会话用自己的读文件工具读、搜，不用一页页翻工具。成员自己知道的那部分——在做什么、做到哪、下一步、坑在哪——用 `room_handoff { text }` 写成 `handoff-<名字>.md` 放在一起。新成员第一次被叫醒时被告知档案在哪；`room_files` 也说。档案不列在成员的文件里；房间删掉时，文件夹里只剩档案就一起删，还有成员的文件就随文件夹进废纸篓。没做：成员被移出或结束之前自动提醒它写交接说明。

- **管理员能用哪些模型，按配置定**（用户定：不想让管理员频繁调用低端模型）。`<数据目录>/room-models.json` 记每个 agent 每个配置下**关掉**的模型，其余都可用。管理员 `room_add` 指定了关掉的模型时被拒绝，并被告知这个配置下可用的；不写配置时按这个 agent 当前的配置算；不写模型的不拦（用配置自己的默认）。`models` 清单里关掉的写着“在某某配置下不给你用”。只管由会话拉起来的会话。用户在 Mac 的房间列表上 `Models` 里逐个开关（`GET /rooms/models`、`PUT /rooms/models/:agent/:profile`）。
- **子代理不进房间**（用户问过，定为保持不变）：它收不了消息、寿命很短，和主 agent 之间本来就有直接交回结果的通道。
- **从名片跳到它的终端**：成员名片上 `Terminal`，切到终端页并显示那个终端。

## 13. 没定的

- 一个会话同时在几个房间里时，排队的消息怎么合并。
- 房间的历史留多久、怎么删。
